# Лабораторные работы №4, №6 и №7

Вариант 14: «Сдача недвижимости в аренду».

Приложение развивает REST API второй лабораторной: добавлены AngularJS и Thymeleaf, вход через Spring Security, HTTPS, CSRF, Logout и журнал изменений. Решение адаптировано из [официального lab4example](https://github.com/wildpierre/trsissamples/tree/master/lab4example) под аренду недвижимости.

Для лабораторной №6 добавлена связь `PROPERTY.OWNER_USER_ID → USERS.USER_ID` с внешним ключом. При создании объекта сервис находит вошедшего пользователя через JPA-репозиторий и сохраняет его как владельца записи. В ответах API и таблице выводится `ownerLogin`; клиент не может назначить владельца сам. Модель содержит три таблицы (`PROPERTY`, `USERS`, `AUDIT_EVENT`), а чтение и запись выполняются через Spring Data JPA. Схему создаёт Liquibase, начальные записи загружаются из `data.sql`.

## Запуск

### Лабораторная №7: два экземпляра и Kafka

Нужны Java 17, Maven и Docker с Compose. Все команды выполняются из `server_app`.

```bash
make kafka
make build
```

Затем в двух отдельных терминалах:

Если JAR отсутствует, `make run1` или `make run2` автоматически соберёт его без тестов. Дождитесь завершения первой сборки, затем запускайте второй экземпляр. После изменения исходников пересоберите приложение командой `make build`.

```bash
make run1
```

```bash
make run2
```

Откройте <https://localhost:8443/> и <https://localhost:9443/>. Подтвердите учебные сертификаты на обоих портах. Войдите как `guest / hello`. Добавьте объект в первом окне, измените его во втором, удалите в любом из них. Изменения и аудит появятся в обоих окнах; страница обновляет данные каждые две секунды. В профиле `replication` у экземпляров разные имена сеансовых cookie (`SESSION_instance-1`, `SESSION_instance-2`), поэтому можно войти в оба окна одного браузера независимо.

Остановить брокер с сохранением его журнала: `docker compose stop`. При повторном запуске — `make kafka`. Не удаляйте том `kafka-data`, если хотите восстановить изменения после перезапуска H2.

Профиль `replication` включает Spring Kafka. Параметры: `APP_PORT`, `APP_INSTANCE_ID`, `KAFKA_BOOTSTRAP_SERVERS` или аргументы `--server.port`, `--app.instance-id`, `--spring.kafka.bootstrap-servers`. У каждого процесса своя H2; одинаковые имена H2 в разных JVM не означают общую базу. Запускайте два JAR после одной сборки: одновременный `mvn spring-boot:run` очищает общий `target` из-за существующей настройки Maven.

#### Обмен событиями

`REST → JPA + REPLICATION_OUTBOX → Kafka (property-changes) → Consumer каждого экземпляра → локальная H2`.

В топик отправляются `CREATE`, `UPDATE`, `DELETE`, полный снимок объекта, логин автора, время, UUID события и имя источника. Топик имеет одну партицию: экземпляры применяют изменения в общем порядке. Каждый запуск получает отдельную группу потребителей и читает журнал с начала, поскольку H2 создаётся заново. Реплицируется недвижимость и аудит, а учебный пользователь `guest` создаётся из `data.sql` в каждой базе; управление учетными записями не реализовано.

Изменение и запись исходящего события сохраняются в одной транзакции. Планировщик отправляет только зафиксированные события и удаляет их из outbox после подтверждения Kafka. При недоступности брокера события остаются для повторной отправки, пока работает процесс. Consumer применяет событие и записывает его UUID в одной транзакции; дубликаты не создают повторный аудит. Получение события не вызывает отправку нового. Собственные события тоже применяются в порядке Kafka — это обеспечивает сходимость при конкурирующих правках; окончательный результат задаёт последнее событие в журнале. В режиме репликации аудит появляется асинхронно после обработки события.

Новые ID — случайные положительные числа до `2^53−1`, точно представимые в JavaScript, вместо независимых локальных счётчиков. Вероятность совпадения мала, но математически не нулевая; для учебной демонстрации этого достаточно. Начальные записи имеют одинаковые ID в обеих базах.

Ограничения учебной конфигурации: один брокер, без отказоустойчивого кластера; восстановление возможно лишь в пределах сохранённого журнала Kafka (по умолчанию срок хранения ограничен настройками брокера). Outbox и таблица обработанных событий находятся в H2 в памяти: при аварийной остановке ещё не доставленные события теряются. REST подтверждает локальную запись, а не синхронизацию всех реплик. Для промышленного применения нужны постоянная БД и политика хранения/снимков состояния.

`make test` запускает существующие проверки REST и интеграционный тест с настоящим Kafka-брокером в JVM, без Docker. Последний проверяет две независимые H2, обмен в обе стороны, удаление, повторную доставку и восстановление второй реплики после перезапуска.

Проверка двух уже работающих HTTPS-экземпляров с реальным входом и CSRF: `python3 tools/verify_replication.py --output verification/https-replication.json`. Скрипт создаёт и удаляет свой тестовый объект, сверяет данные и аудит. В `verification/` сохранены результаты выполненных проверок. Отчёт — `ОтчетЛР7Кочнев4431.docx`, редактируемый исходник — одноимённый HTML; `python3 tools/build_lab7_report.py` пересоздаёт HTML из шаблона ЛР6, исходников и протоколов проверки. Конвертация в DOCX: `libreoffice --headless --convert-to docx --outdir . ОтчетЛР7Кочнев4431.html`.

### Запуск без репликации (лабы №4 и №6)

```bash
make
```

`make` запускает тесты и HTTPS-сервер. Для запуска без тестов используйте `make run`. Maven создаёт учебный самоподписанный сертификат в `target/keystore.p12`. Браузер при первом открытии попросит подтвердить его.

- Страница объектов: <https://localhost:8443/>
- Вход: <https://localhost:8443/login>
- Swagger UI: <https://localhost:8443/swagger-ui.html>
- OpenAPI JSON: <https://localhost:8443/api-docs>
- REST API: <https://localhost:8443/api/properties>

Учебный логин — `guest`, пароль — `hello` (как в примере преподавателя). В базе хранится BCrypt-хэш. H2 находится в памяти: изменения и аудит сбрасываются при остановке сервера. Сертификат и учётные данные предназначены для демонстрации лабораторной.

Исходное OpenAPI v3-описание для отчёта находится в `openapi.yaml`. Дополнительные команды: `make test`, `make build`, `make clean`, `make help`.

## Методы

| HTTP | URI | Код успеха | Доступ |
|---|---|---:|---|
| GET | `/api/properties` | 200 | всем |
| GET | `/api/properties/{id}` | 200 | всем |
| POST | `/api/properties` | 201 | после входа + CSRF |
| PUT | `/api/properties/{id}` | 200 | после входа + CSRF |
| DELETE | `/api/properties/{id}` | 204 | после входа + CSRF |
| GET | `/api/audit` | 200 | после входа |

Пример JSON для POST/PUT:

```json
{
  "address": "Санкт-Петербург, Литейный проспект, 10",
  "type": "APARTMENT",
  "area": 42.5,
  "rooms": 2,
  "monthlyRent": 55000,
  "available": true
}
```

Допустимые типы: `APARTMENT`, `HOUSE`, `ROOM`, `COMMERCIAL`.

На защите можно показать: анонимный просмотр, вход, изменение через AJAX, HTTP 403 без CSRF, журнал `CREATE/UPDATE/DELETE`, кнопку выхода и связь недвижимости с пользователем через `OWNER_USER_ID`. Тест `databaseRejectsPropertyWithUnknownOwner` проверяет, что внешний ключ действует на уровне БД.
