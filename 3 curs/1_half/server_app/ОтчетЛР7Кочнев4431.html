Задание:

Цель работы — реализация простой системы распределённой репликации по модели «писатели — читатели».

  1. Развернуть Apache Kafka.
  2. Обеспечить запуск нескольких экземпляров приложения со встроенной базой данных на разных портах.
  3. Реализовать Producer, отправляющий события каждой операции записи, и Consumer, применяющий изменения к локальной базе.
  4. Продемонстрировать доступность записанных данных в другом экземпляре.

Описание разрабатываемого продукта:

Вариант 14 — «Сдача недвижимости в аренду». Работа выполнена на основе server_app из лабораторных №4 и №6. В приложении используются Spring Boot, Spring Security, HTTPS, Thymeleaf, AngularJS, Spring Data JPA, H2 и Liquibase. Добавлены Spring Kafka, Producer и Consumer, реплицирующие объекты недвижимости и журнал аудита.

Выбран основной вариант задания с двумя встроенными базами H2. Пример преподавателя lab78example использует альтернативный вариант с PostgreSQL, Kafka Connect и Debezium; в данной работе изменения публикует само приложение.

Архитектура и порядок работы:

Экземпляр 1 (HTTPS 8443, H2 №1)

           ↕ Producer / Consumer

     Kafka: property-changes, 1 партиция

           ↕ Producer / Consumer

Экземпляр 2 (HTTPS 9443, H2 №2)

Каждый экземпляр имеет собственную базу H2 и отдельную группу потребителей Kafka. Поэтому каждое событие получает каждый экземпляр, а не только один участник общей группы. Одна партиция задаёт одинаковый порядок применения событий на всех репликах.

После создания, изменения или удаления объекта сервис записывает событие в REPLICATION_OUTBOX в той же транзакции, что и локальные данные. Планировщик отправляет зафиксированное событие в Kafka и удаляет его из outbox только после подтверждения брокера. Consumer применяет изменение, записывает аудит и UUID события в REPLICATION_APPLIED в одной транзакции.

Повторно доставленное событие пропускается по UUID. Consumer не вызывает методы, формирующие новые события, что предотвращает зацикливание. Собственные события также применяются в порядке Kafka: при конкурирующих изменениях итоговое состояние определяется последним событием в журнале.

Событие содержит UUID, имя источника, действие CREATE/UPDATE/DELETE, логин пользователя, время и полный снимок объекта. Связь PROPERTY → USERS сохраняется: пользователь определяется по логину. Учебная учётная запись guest создаётся в каждой базе из data.sql.

При каждом запуске группа формируется как properties-<instance-id>-<UUID>. Это необходимо, поскольку H2 в памяти создаётся заново и должна перечитать журнал с начала. Разные имена cookie позволяют войти в два экземпляра из одного браузера.

3. Регистрация исходящего события в транзакции (ReplicationEvents.java):

    @Transactional(propagation = Propagation.MANDATORY)

    public boolean record(String action, PropertyDTO property, String actor) {

        if (!enabled) return false;

        PropertyChange change = new PropertyChange(UUID.randomUUID().toString(), instance,

                action, actor, Instant.now(), property);

        OutboxEvent event = new OutboxEvent();

        event.setId(change.eventId());

        event.setPropertyId(property.getId());

        event.setCreatedAt(change.occurredAt());

        try {

            event.setPayload(mapper.writeValueAsString(change));

        } catch (JsonProcessingException exception) {

            throw new IllegalStateException("Cannot serialize replication event", exception);

        }

        outbox.save(event);

        return true;

    }

4. Отправка через KafkaTemplate (OutboxPublisher.java):

    @Scheduled(fixedDelayString = "${app.replication.publish-delay-ms:250}")

    public void publish() {

        for (OutboxEvent event : outbox.findTop100ByOrderByCreatedAtAscIdAsc()) {

            try {

                kafka.send(topic, event.getPropertyId().toString(), event.getPayload())

                        .get(10, TimeUnit.SECONDS);

                outbox.deleteById(event.getId());

            } catch (Exception exception) {

                if (exception instanceof InterruptedException) Thread.currentThread().interrupt();

                log.warn("Kafka delivery pending for event {}: {}", event.getId(), exception.toString());

                return; // Retain the event for retry; do not overtake it with newer events.

            }

        }

    }

5. Основные шаги Consumer (PropertyChangeConsumer.java):

@Transactional

@KafkaListener(topics = "${app.replication.topic}",

        groupId = "#{@replicationGroup}")

public void receive(String json) throws JsonProcessingException {

    PropertyChange event = mapper.readValue(json, PropertyChange.class);

    if (applied.existsById(event.eventId())) return;

    // DELETE: удалить объект, если он существует.

    // CREATE/UPDATE: найти или создать объект по ID,

    // перенести поля DTO, найти пользователя и вызвать save().

    // Записать аудит с исходными actor, action, occurredAt.

    applied.save(new AppliedEvent(event.eventId()));

}

Фрагменты с комментариями сокращены; полный код расположен в пакете replication. Применение данных и отметка обработки фиксируются вместе, а смещение Kafka подтверждается после успешной обработки записи. При ошибке обработка повторяется.

6. Идентификаторы объектов (PropertyServiceImpl.java):

entity.setId(UUID.randomUUID().getMostSignificantBits()

        & 0x001fffffffffffffL);

Независимые счётчики двух баз могли бы создать один и тот же ID. Новые ID генерируются случайно в пределах точных целых чисел JavaScript, до 2^53−1. Вероятность случайного совпадения мала, но не равна нулю. Начальные записи имеют одинаковые ID в обеих базах.

Ограничения реализации:

Репликация асинхронна: успешный REST-ответ подтверждает локальную запись, но не завершение синхронизации всех экземпляров. В режиме репликации журнал аудита пополняется после обработки события. События в outbox повторяются при временной недоступности Kafka, пока работает процесс.

H2, outbox и отметки обработки находятся в памяти: аварийная остановка до доставки события может привести к его потере. Восстановление выполненных изменений зависит от сохранности и срока хранения журнала Kafka. Конфигурация использует один брокер и предназначена для учебной демонстрации; для промышленного применения нужны постоянная база, политика снимков состояния и отказоустойчивость брокера.

В лабораторной работе №7 реализована распределённая репликация данных недвижимости через Apache Kafka. Два экземпляра приложения работают на разных HTTPS-портах с независимыми H2 и обмениваются событиями создания, изменения и удаления. Добавлены защита от повторного применения событий, предотвращение зацикливания и восстановление из журнала. Работа подтверждена автоматическими тестами и проверкой через HTTPS API.
